# CURSOR_WORKFLOW — правила для Cursor (ScreenerPRO)

Этот документ обязателен для **каждой задачи** в репозитории. Владелец продукта **не программист** — отчёт должен быть понятен без жаргона.

Связанные файлы:

- `PROJECT_CONTEXT.md` — технический конспект
- `PRODUCT_VISION.md` — продукт и UX
- `AI_SESSION_STATE.md` — журнал последней итерации

---

## 1. После каждой задачи — отчёт в чате

В конце ответа Cursor **всегда** включает блок:

### Изменённые файлы

Список путей (созданы / изменены / удалены).

### Что изменилось простыми словами

2–5 предложений: что увидит пользователь в интерфейсе или в поведении сайта. Без имён функций, если можно обойтись.

### Что проверить в браузере

Нумерованный чек-лист URL и действий («открой …, нажми …, убедись что …»).

### Команды для проверки (если запускались)

Например: `pnpm -C frontend build` — успех / ошибка.

---

## 2. Язык и объём правок

| Правило | Пояснение |
|---------|-----------|
| **Простой язык** | «Таблица скринера» вместо «TanStack virtualizer» |
| **Минимальный diff** | Не переписывать большие файлы целиком без явной просьбы |
| **Только задача** | UI-задача → не менять формулы in-play; data-задача → не трогать академию |
| **Не трогать секреты** | Не коммитить и не выводить в чат `.env`, ключи API, токены |
| **Не менять `.env`** | Только `.env.example` с плейсхолдерами, если нужна новая переменная |

---

## 3. Проверки после изменений кода

Если задача затрагивает `frontend/`:

1. По возможности выполнить:  
   `pnpm -C frontend build`  
   (или как минимум убедиться, что TypeScript не сломан — build предпочтительнее).
2. При ошибках — исправить или явно описать блокер в отчёте.
3. Не оставлять «сломанный build» без объяснения.

Мелкая правка только в `.md` — build не обязателен.

---

## 4. Обновление документации

| Ситуация | Файл |
|----------|------|
| Любая **крупная** задача (новый экран, API, смена данных) | `AI_SESSION_STATE.md` |
| Смена архитектуры, маршрутов, источников данных | `PROJECT_CONTEXT.md` (точечно, не переписывать весь файл) |
| Смена продуктовой идеи, UX-принципов, roadmap | `PRODUCT_VISION.md` |

**Крупная задача** = больше ~3 файлов кода или влияние на скринер / материалы / API.

В `AI_SESSION_STATE.md` обновить:

- Текущая задача  
- Что сделано  
- Какие файлы менялись  
- Что работает / что проверить  
- Следующий шаг  
- Последний промпт / краткий итог ответа

---

## 6. Типичный поток с ChatGPT

1. Владелец согласует задачу с ChatGPT → получает формулировку и критерии готовности.
2. Промпт в Cursor: цель + ссылки на `PRODUCT_VISION.md` / `AI_SESSION_STATE.md` + «следуй docs/CURSOR_WORKFLOW.md».
3. Cursor делает изменения + отчёт + обновляет `AI_SESSION_STATE.md` при необходимости.
4. Владелец проверяет по чек-листу; при баге — новый промпт с текстом ошибки и URL.

---

## 7. Что не делать без запроса

- Массовый рефакторинг «для красоты»
- Обновление major-версий Next/React/Prisma
- `git push --force`, изменение git config
- Удаление mock/fallback до появления замены
- Коммиты (только если пользователь явно попросил)
